# Day13-14 RAG 评测

## 今日目标

- 准备 30 个 RAG 测试问题
- 批量评测 Recall@K、引用正确性、响应时间、Token 消耗
- 整理失败案例
- 完成一个可评测、可解释的 RAG 结果集

## 为什么要做评测

RAG 不只是“能回答”，还要知道：

- 有没有召回到正确资料
- 回答有没有依据
- 引用是不是对的
- 不知道时会不会乱答
- 不同用户的数据会不会串
- 响应速度和成本是否合理

如果不做评测，就很难判断系统到底是真的变强了，还是只是偶然答对。

## 测试集设计

本次共准备 30 个问题，分为 6 类：

- 直接答案
- 换一种问法
- 关键词命中
- 不知道时拒答
- 不同用户隔离
- 文档更新和引用来源

测试文件：

- `eval_questions.jsonl`

每条问题都包含：

- `id`
- `category`
- `user_id`
- `question`
- `top_k`
- `should_answer`
- `expected_answer_keywords`
- `expected_source_filename`
- `expected_source_contains`

## 评测脚本

本次使用：

- `eval_runner.py`

脚本会：

```text
读取 30 个测试问题
-> 调用 /rag/answer
-> 记录返回结果
-> 判断答案是否命中关键字
-> 判断引用是否来自正确来源
-> 记录耗时
-> 输出 eval_results.jsonl
```

输出文件：

- `eval_results.jsonl`

## 评测指标

### Recall@K

看正确 chunk 是否出现在返回的 sources 里。

如果正确资料被召回到 Top-K，就算召回成功。

### 回答正确性

看 answer 是否包含预期关键字。

例如：

```text
问题：小乐的身高是多少？
期望：185cm
```

### 引用正确性

看 sources 是否来自正确文件、正确内容。

### 响应时间

记录每道题的接口耗时，单位秒。

本次平均响应时间约为：

```text
1.231s
```

### Token 消耗

如果接口返回 usage，就记录。

当前结果里大部分用例还没有直接拿到 token usage，因此这项在本次评测中暂时记为可扩展项。

## 本次结果

本次共评测 30 题。

```text
通过：23
失败：7
通过率：76.67%
```

其中：

- 召回整体是可用的
- 基础拒答是有效的
- 用户隔离整体成立
- 但仍有少量生成偏差和测试预期不一致

## 失败案例

失败案例已经单独整理在：

- `failure_cases.md`

主要问题包括：

- 测试集里文件名预期不一致
- 某些问题依赖 metadata 检索
- 部分问题检索到了，但模型生成没抽出正确答案
- 模型被问题中的其他用户编号带偏
- 当前还没有完整文档版本管理

## 当前系统能力

本次评测说明当前系统已经具备：

- 基础 RAG 问答
- 引用来源返回
- 不知道时拒答
- 不同用户数据隔离
- 文档更新的简化版替换式处理

## 还可以继续优化的方向

- 给测试环境做固定初始化，避免旧数据干扰评测
- 增加 metadata 检索能力
- 强化 system prompt 的权限边界
- 分开统计召回成功率和生成正确率
- 增加文档版本管理
- 增加更细的引用校验

## 我对 Day13-14 的理解

Day13-14 的重点不是再加功能，而是验证功能是否真的可靠。

通过这次评测，我能更清楚地区分：

- 检索是否正确
- 模型是否答对
- 引用是否可信
- 拒答是否合理
- 数据隔离是否生效

这一步让 RAG 从“能演示”变成“能评估”。
