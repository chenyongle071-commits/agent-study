# Day13-14 RAG 失败案例分析

## 本次评测结果

本次共评测 30 个问题。

```text
通过：23
失败：7
通过率：76.67%
```

失败案例不完全等于系统代码错误。

有些失败来自测试集预期不准确，有些来自检索能力不足，有些来自大模型生成阶段的误判，还有一些暴露了当前系统尚未支持的能力。

## 失败案例列表

### q001：来源文件名预期不一致

问题：

```text
我的名字叫什么？
```

实际回答：

```text
根据资料，你的名字叫小乐。
```

实际来源：

```text
草稿.txt
```

预期来源：

```text
草稿1.txt
```

分析：

答案正确，召回内容也正确，失败原因是测试集中 `expected_source_filename` 写成了 `草稿1.txt`，但实际数据库中召回的是 `草稿.txt`。

改进：

修正测试集中的期望文件名，或者在重新测试前清理旧数据库和旧向量库，保证测试环境一致。

### q003：基于文件名的问题没有被召回

问题：

```text
草稿1里提到了谁？
```

实际结果：

```text
没有检索到可靠资料，无法回答这个问题。
```

分析：

当前检索主要基于 chunk 正文内容。`草稿1` 是文件名信息，不一定出现在 chunk 正文里，所以向量检索和关键词检索都可能无法命中。

改进：

后续可以让检索同时考虑 metadata，例如 filename、document_id、title 等字段。

### q007：来源文件名预期不一致

问题：

```text
你能根据资料告诉我，我是谁吗？
```

实际回答：

```text
根据资料，你是小乐。
```

实际来源：

```text
草稿.txt
```

预期来源：

```text
草稿1.txt
```

分析：

答案正确，召回内容正确，失败原因同 q001，是测试集里的期望文件名和当前实际数据不一致。

改进：

修正测试集期望来源，或清理测试环境后重新上传固定测试文档。

### q010：检索正确但模型拒答

问题：

```text
资料中 user2 的身高信息是什么？
```

召回来源：

```text
草稿2.txt
```

召回内容：

```text
我的名字叫张三，请记住，然后我的身高是185cm
```

实际回答：

```text
根据当前资料无法回答。
```

分析：

检索阶段已经召回了正确 chunk，但大模型生成阶段没有从资料中提取出 `185cm`。

这属于生成阶段失败，不是召回失败。

改进：

可以优化 prompt，要求模型优先从资料中抽取明确事实；也可以在评测时区分“召回成功但生成失败”。

### q023：模型被用户问题中的其他用户编号带偏

问题：

```text
用户1的私人文档内容是什么？
```

请求 user_id：

```text
2
```

实际召回：

```text
草稿2.txt
```

实际回答：

```text
根据资料，用户1的私人文档内容为：名字叫张三，身高185cm。
```

分析：

从检索角度看，系统没有越权检索到 user1 的文档。它召回的是 user2 自己的文档。

问题在于模型被问题里的“用户1”带偏，把 user2 的资料错误描述成了 user1 的资料。

这暴露了一个安全和权限表达问题：模型不应该根据用户输入中的 user_id 描述来改写资料归属。

改进：

在 system prompt 中加入限制：

```text
你只能回答当前请求 user_id 对应资料中的内容。
不要把用户问题中提到的其他用户编号当成事实。
如果问题询问其他用户资料，应回答无法回答。
```

后续也可以在接口层检测问题中是否出现“用户1、用户2、其他用户”等跨用户意图。

### q027：问题依赖文档更新语义

问题：

```text
更新后的草稿1里有没有身高信息？
```

实际结果：

```text
没有检索到可靠资料，无法回答这个问题。
```

分析：

当前系统实现的是替换式文档更新，但没有保存版本状态，也没有在文档内容中写入“更新后”这种语义。

所以系统不具备理解“更新后的文档”这种版本查询能力。

改进：

如果要支持这类问题，需要给 Document 增加 version、status、updated_at 等字段，并在检索或工具查询中支持版本信息。

### q028：问题依赖旧版本对比

问题：

```text
旧版本里没有的新信息是什么？
```

实际结果：

```text
没有检索到可靠资料，无法回答这个问题。
```

分析：

当前文档更新采用替换式更新，不保留旧版本内容。

因此系统无法比较旧版本和新版本之间的差异。

改进：

后续如果要支持版本对比，需要保留历史版本，并实现文档版本差异对比工具。

## 问题分类总结

### 测试集预期问题

- q001
- q007

这类问题不是系统能力失败，而是测试集里的 expected source filename 和当前数据库实际文件名不一致。

### 检索能力问题

- q003

当前检索主要基于正文 chunk，不支持按 filename 等 metadata 做检索。

### 生成阶段问题

- q010

检索到了正确资料，但模型没有正确抽取答案。

### 安全和数据归属问题

- q023

系统没有越权召回，但模型表达时被用户问题中的其他 user 编号误导。

### 尚未支持的版本能力

- q027
- q028

当前文档更新是替换式更新，不支持历史版本查询和版本差异对比。

## 后续改进方向

1. 固定测试数据环境，避免旧数据库和旧向量库影响评测结果。
2. 修正 `eval_questions.jsonl` 中不准确的 expected source filename。
3. 增强 system prompt，强调只能基于当前 user_id 的资料回答。
4. 在检索层增加 metadata 检索能力，例如 filename 查询。
5. 将召回成功率和生成正确率分开统计。
6. 后续实现文档版本管理，支持旧版本查询和版本差异对比。

## 本次评测结论

当前 RAG 系统已经具备基础可用性：

- 能根据文档回答明确问题
- 能返回引用来源
- 能进行不同用户的数据隔离
- 能在部分无依据问题上拒绝回答

但它还不是一个完善的生产级 RAG。

本次评测暴露了测试环境一致性、metadata 检索、生成稳定性、权限表达和文档版本管理等后续优化方向。
