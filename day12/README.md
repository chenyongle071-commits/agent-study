# Day12 RAG 工程化问题处理

## 今日目标

- 处理无关召回

## 为什么要做 Day12

前几天已经实现了基础 RAG：

```text
上传文档
-> 切分 chunk
-> 向量化
-> 检索
-> 生成答案
-> 返回引用来源
```

Day12 关注的是 RAG 在真实项目中更容易出问题的地方。

真实项目里，RAG 不只是“能回答”，还要能控制：

- 什么时候不能回答
- 能不能避免无关资料干扰
- 不同用户的数据会不会串
- 重复文档和文档更新怎么处理

## 无关召回是什么

向量数据库在检索时通常会尽量返回 Top-K 个结果。

即使用户问的问题和文档关系不大，它也可能返回一个“相对最像”的 chunk。

例如文档里只有：

```text
我的名字叫小乐
```

用户问：

```text
我身高多高？
```

向量数据库仍然可能返回这个 chunk。

这就是无关召回。

## 当前解决方式

在 `hybrid_retrieve_chunks()` 中增加了 `max_vector_distance`。

```python
max_vector_distance: float = 1.0
```

向量检索结果只有在满足下面条件时才会保留：

```python
result["distance"] <= max_vector_distance
```

也就是说：

```text
distance 太大
-> 认为不可靠
-> 不交给大模型
```

## 不知道时拒绝回答

如果关键词检索和向量检索都没有找到可靠 chunk，接口会直接返回错误：

```json
{
  "detail": "没有检索到可靠资料，无法回答这个问题。"
}
```

这样可以避免模型在没有依据时乱编答案。

RAG 项目里，这一点很重要。

一个好的 RAG 系统不应该只会回答，还应该知道什么时候不能回答。

## 数据隔离

当前系统通过 `user_id` 做数据隔离。

关键词检索时：

```python
.where(Chunk.user_id == user_id)
```

向量检索时：

```python
where={"user_id": user_id}
```

这样 user1 查询时只能检索 user1 的文档，user2 查询时只能检索 user2 的文档。

测试 1：


结果：


测试 2：

```json
}
```

结果：

```text
根据资料，您的名字叫张三。
```

测试 3：

```json
{
```


说明 user1 没有查到 user2 的文档，数据隔离生效。

## 重复内容

当前项目已经通过 `content_hash` 做了基础重复检测。

如果同一个用户上传完全相同内容的文件，系统可以识别它是重复内容，避免重复保存。

当前主要解决的是文件级重复：

```text
整个文件内容完全一样
-> hash 一样
-> 判断为重复上传
```

还没有完整处理 chunk 级重复。

## 文档更新

文档更新是指：

```text
同一个用户
+ 同一个文件名
+ 文件内容发生变化
```

当前项目实现了简化版文档更新。

判断规则：

```text
同 user_id + 同 filename + content_hash 不同
-> 认为是文档更新
```

处理流程：

```text
查询当前用户同名旧文档
-> 如果 content_hash 相同，拒绝重复上传
-> 如果 content_hash 不同，认为是新版本
-> 删除旧文档对应的 Chroma 向量
-> 删除旧 chunks
-> 删除旧 Document
-> 保存新 Document
-> 保存新 chunks
-> 重新调用 /documents/{document_id}/index 进行向量化
```

当前实现属于“替换式更新”，不会保留历史版本。

真实项目后续可以升级成：

```text
保留旧版本
给 Document 增加 version / status / updated_at
只让 active 文档参与检索
```

## 文档更新测试

第一次上传：

```text
我的名字叫小乐
```

重新上传同名文件：

```text
我的名字叫小乐，小乐的身高是185cm
```

重新索引后提问：

```json
{
  "user_id": 1,
  "query": "小乐身高多高？",
  "top_k": 3,
  "temperature": 0.3
}
```

返回：

```text
根据资料，小乐身高185cm。
```

说明文档更新后的新内容已经参与 RAG 问答。

## 我对 Day12 的理解

Day12 的重点是让 RAG 更可靠。

基础 RAG 只解决“能不能找到资料并回答”，但真实项目还要处理很多边界情况。

现在系统已经能做到：

- 对无关召回做基础过滤
- 没有可靠资料时拒绝回答
- 不同用户之间的数据隔离
- 对完全重复文件做基础识别

文档更新已经实现了简化版替换式更新，后续还可以继续增强成版本管理。
